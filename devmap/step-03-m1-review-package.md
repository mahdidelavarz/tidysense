## Contract inventory

| Contract | Evidence | Retention/access |
|---|---|---|
| IDs, ownership, optimistic version | `Project.Version` starts at 1, conditional owned update advances once, stale version yields scoped 409, cross-user lookup yields 404 | Canonical Project ownership; no new Project write API |
| Idempotency and CommandResult | Unique `(UserId, IdempotencyKey)` claim; server-calculated request hash; matching replay returns one result; mismatch yields 409; final rejection and conflict are durable results; unexpected failure rolls back | Idempotency R4; CommandResult R1; only owner may retrieve a result |
| Event envelope and outbox | Versioned event envelope contains actor, aggregate/version, transaction and correlation fields plus optional evidence links; one unique outbox intent per event in the same transaction. Every emitted type/version requires a registered payload schema. | DomainEvent R1; OutboxMessage R4; only schema-approved fields, JSON object, maximum 4,096 UTF-8 bytes, no authentication material or unnecessary direct PII |
| API errors and observability | Shared Problem Details code/messageKey/retryable/trace/correlation fields, safe version details, validation errors; `/health/live` is independent of database readiness | Structured command logs exclude bodies, OTPs, tokens and provider secrets |

The current executor accepts one synchronous deterministic mutation callback. Callers must authenticate and scope by owner before version checking, calculate the hash over normalized command fields and expected versions, supply a future expiry for a new key, and supply an approved event payload. A replay checks the same user's key and hash and returns historical `CommandResult` without changing canonical state. Product-specific terminal no-op behavior after record deletion, ActionConfirmation recovery, and outbox publishing remain with their first consuming steps.

### Envelope fields and data boundary

| Field group | M1 requirement and current implementation | Privacy meaning |
|---|---|---|
| Required identity/provenance | `eventId`, `eventType`, `eventVersion`, `occurredAt`, `recordedAt`, `userId`, `actor`, `aggregateType`, `aggregateId`, `aggregateVersion`, `transactionId`, `correlationId`, `payload`; `retentionClass` is also required in the implemented row. Current M1 is user-scoped; the accepted authority allows `userId` **or** `workspaceId`, but no workspace model is implemented. | User/aggregate and correlation identifiers are linkable metadata; apply the record's access and retention class. `eventType`/`aggregateType` are controlled classification codes, not free-text product content. |
| Optional linkage | `causationId`, `commandResultId`, `proposalId`, `confirmationId`, `reconcileSessionId`, `ruleId`, `ruleVersion`. The database permits nulls. The current successful-command path sets `commandResultId` to the authoritative R1 `CommandResult.Id`; it does not claim to store an originating command identity. The other optional fields are not currently populated. | These link to potentially sensitive product histories. A link does not grant broader access to the linked record. Their exact later-slice semantics need consumer review. An actual future originating `commandId` would require a separately reviewed contract. |
| Product/domain detail | `payload` (`PayloadJson` in code) is the only open JSON field. It may contain approved, minimal structured change facts, safe reason codes and non-sensitive before/after values needed for audit. Aggregate identifiers and approved linkage fields may identify affected entities; they must not duplicate entity snapshots. | R1 retention makes payload minimization consequential. No secrets, OTPs/digests, credentials, tokens, API keys, full phone numbers, raw prompts/responses, imported content, unrestricted user notes/descriptions or unnecessary PII belong in payload **or in string metadata fields** such as type, rule or correlation IDs. |

`EventPayloadValidator` is the reusable payload-content gate. Each producer must register one unique schema for its `(eventType, eventVersion)` before emission. The schema names every allowed and required top-level field and validates that field's complete JSON value; unknown, duplicate, missing or invalid fields fail before commit. Schema registration and nested payloads reject credential/authentication names including secrets, OTPs, passwords, API keys, cookies, JWT/session/access/refresh tokens and direct phone/email identity. Each owning slice must still review allowed values for minimization and unnecessary PII rather than treating registration as blanket approval.

The shared policy requires a JSON **object** payload of at most **4,096 UTF-8 bytes**. `CommandExecutionService` applies it before persistence, and `AppDbContext.SaveChanges` applies it to every added or modified `DomainEvent`, including callers outside the command executor. PostgreSQL independently requires an object and enforces the same 4,096-byte ceiling, covering a bypass of EF. The database does not attempt to reproduce each code-defined field schema, so application writes must use the registered validator. The outbox row contains only an event reference and delivery metadata; there is no second outbox payload path. Event/aggregate versions remain positive, `occurredAt` is UTC, type/correlation strings are bounded, and the current executor writes `USER` and R1.

### Retention/access decision and unresolved meanings

| Persisted evidence | Current class | Intent and current limitation |
|---|---|---|
| `DomainEvent` for canonical/audit mutation | R1 `CANONICAL_AUDIT` | Durable historical fact, not canonical current state; only approved, minimized user-visible or de-identified analytics projections. The model defaults to R1; the database does not constrain class values. This table is not approved as a generic store for R2/R3/R4/R5/R6 content. |
| `CommandResult` | R1 `CANONICAL_AUDIT` | Durable proof of success, conflict or final rejection; owner-scoped retrieval. `IdempotencyRecordId` is retained as an unvalidated correlation value and is not a foreign key. It must not be inferred from an outbox delivery status. |
| `IdempotencyRecord` | R4 `OPERATIONAL_DIAGNOSTICS` | Replay boundary with caller-supplied expiry, not durable product truth; request hash is stored rather than a request body. |
| `OutboxMessage` | R4 `OPERATIONAL_DIAGNOSTICS` | Delivery intent/status only; its referenced `DomainEvent` remains R1 even after operational delivery metadata is removed. |

Exact R1/R4 durations, legal basis, deletion/anonymization and restore mechanics remain for legal/security and operations review; the M1 class assignment does not invent a duration. No R4 purge job exists. Migration `20260926085120_HardenStep3EventContract` removes the R1 `CommandResult` foreign-key dependency on R4 `IdempotencyRecord`; the retained ID is correlation only. R4 idempotency and outbox rows can now be removed independently while the R1 result/event remains. Downgrade recreates a minimal R4 correlation row when required before restoring the old foreign key, so rollback remains executable after R4 cleanup.

`DomainEvent.UserId`, aggregate/link IDs and `correlationId` remain linkable pseudonymous data; privacy deletion/tombstoning mechanics are not implemented. `CommandResultId` has one explicit meaning: the linked authoritative result, enforced by an R1-to-R1 foreign key. The migration preserves old values that resolve to a result and clears unverifiable values created under the former ambiguous name. Optional proposal/confirmation/session/rule links have no current emitter; their exact payload and retention implications remain with the first consuming slice. Pre-commit Planning/Reconcile records may be R2/R3 while committed decision evidence is R1; a later producer must classify each actual event before use. CaptureItem event classification is explicitly unresolved by Discussion 026 and belongs to its first producing slice.
