# Active Conventions

- Product name TidySense; repository roots `/frontend` and `/backend`.
- API `/api/v1`; no dual obsolete routes; camelCase JSON; RFC 9457 via `IExceptionHandler`.
- Guid identities; DateTimeOffset instants; DateOnly local dates; one configured pilot IANA timezone.
- Keep existing EF/PostgreSQL identifier naming; no provider-driven naming rewrite.
- JWT HttpOnly cookie + sessionEpoch; Kavenegar; backend security authority. The Android app alone uses the same JWT as a bearer token with `X-TidySense-Client: native` ([ADR-008](../decisions/ADR-008-native-client-authentication.md)).
- Consequential writes use owned optimistic versions, user-scoped idempotency, an authoritative CommandResult, and domain event plus outbox intent in one PostgreSQL transaction; M2 owns product-command lock.
- Every durable domain event uses a registered `(eventType, eventVersion)` payload schema with explicitly approved fields. Payloads are JSON objects up to 4,096 UTF-8 bytes, exclude authentication material and unnecessary direct PII, and are validated both by the write path and database size/shape constraints. Outbox rows reference rather than copy R1 event payloads; `CommandResultId` means the linked R1 result, and R4 idempotency/outbox rows remain independently deletable.
- Feature-oriented backend with direct EF for simple work and only justified narrow ports/repositories; no generic repository.
- Feature-oriented frontend (`types`, one `services` file, one `hooks` file, `components` per feature), TanStack file routes, generated OpenAPI types + Zod forms.
- UI follows `frontend/design-system.md`: no top bar; an icon rail plugged into a floating page panel on desktop, a five-place tab bar (Planning in the middle as the moonstone) with a floating create button on phones (Discussion 030 §3 replaces this with four tabs and a centre «+» on the phone web and the app, built in MOB-05), and an account panel for everything else; the AI is always the moonstone (`--ai-*` tokens), never a button colour; create/edit in sheets; one primary action per page; Jalali dates and Persian digits; light and dark themes from one token set (no per-component dark styles); Solar icons compiled in through `shared/ui/icons`; Vazirmatn with Noto Naskh Arabic for titles.
- From 1024px a page may have its own desktop layout: the page renders one layout chosen by `useIsDesktop()`, never both hidden by CSS. The desktop layout reads the same queries and calls the same actions as the phone, and every extra figure is derived from data the phone already reads; it estimates nothing (028 §5). See `frontend/layout-and-navigation.md`, *Desktop layouts*.
- Cursor pagination with stable ordering and allowlisted feature filters/sorts.
- Goal and Project use persisted review snapshots, explicit terminal transitions and owner-scoped versions. Goal terminal and Project attach/reparent serialize on the Goal; later child modules must extend the same blocker preview before permitting child creation.
- Ending a parent and a Project's state live in `ParentLifecycle` (owner decision 2026-10-19, 012 §4 and 015 §9 notes). A stop (Goal `ABANDONED`, Project `STOPPED`) has no blockers: its preview lists every cascade (Projects stopped, open Tasks dropped, Routines stopped), the command rebuilds the list under locks and refuses any difference with `CONFIRMATION_STALE`. A Project is never `COMPLETED` by hand (`PROJECT_COMPLETES_BY_PROGRESS`). Every command that changes a Task's status or place calls `SettleProjectsAsync` for the Projects it touched, after locking them parents first: no open and at least one done Task completes the Project and stops its Routines (`PROJECT_COMPLETED` v2, cause `PROGRESS`); an open Task again reopens it (`PROJECT_REOPENED`). Creating, moving or restoring a Task into a `COMPLETED` Project is allowed (`allowCompletedProject`) and reopens it. Stopping a Routine deletes its pending occurrences from today on, so it leaves Today at once.
- A command that deterministically changes other aggregates returns them as `CascadeEvents`: one event per changed child, actor `SYSTEM_DETERMINISTIC`, sharing the parent's transaction id. Deterministic system work outside a user command (Routine occurrence creation and Missed resolution) writes its own `SYSTEM_DETERMINISTIC` event and outbox row in the same transaction as the change.
- Routine occurrences are materialized lazily under a Routine row lock, never past the current local date; schedule edits are prospective. See `step-06-routine-acceptance.md`.
- A cascade event may set actor `USER` when the user confirmed that exact member (each Task of a bulk Reconcile action, the Task or Routine created from a capture); otherwise it stays `SYSTEM_DETERMINISTIC`.
- Reconcile facts, severity and rule matches are derived on every read by pure code (`ReconcileRules`); nothing derived (carry count, overdue, severity) is stored on a work record. Carry count and Keep acknowledgement come from Task events.
- A multi-entity mutation is a stored `ActionConfirmation`: the server builds the preview, the client submits only its id and warning acknowledgements, and submit rebuilds the preview under locks and rejects any difference with `CONFIRMATION_STALE`. The only exceptions are Reconcile's one-tap «انجام شد» and «امروز» on a single Task (027 §6): applied by the ordinary command on tap, recorded as a `ReconcileQuickAction`, and undoable through a deterministic command while the session is open and the Task unchanged. See `step-07-capture-reconcile-acceptance.md` 26–31. The other exception is a person's own sequence change (029 §9.2, 025 §16): «بعد از…», a step earlier or later, or out of the order is one `CHANGE_TASK_SEQUENCE` command on the Task acted on (actions `FOLLOW`, `MOVE_EARLIER`, `MOVE_LATER`, `MOVE_TO` for a dragged step, `LEAVE`). The server builds its preview and does not store it; the command carries the id and version of every Task the preview read and is refused (`SEQUENCE_PREVIEW_STALE`, or `CONFLICT_STALE_VERSION`) if any changed. Every other Task it re-places is a cascade event with actor `USER`, because the person saw it in the preview. A stored `ActionConfirmation` would need a third subject for one small, one-scope edit. A new Task that follows another is the same rule inside `CREATE_TASK`: `POST /tasks/sequence-preview` previews it, and the create request carries `follow` (predecessor and expected members), so the Task and its place are made together or not at all. A done tick is undone on the same tick (018 note): `UNDO_COMPLETE_TASK` reopens a Task exactly as it was, refused while a later step of its sequence is done (`SEQUENCE_LATER_STEP_DONE`); `UNDO_ROUTINE_OCCURRENCE_DONE` returns a slot to pending while its window is open, else to missed. Restore is for dropped Tasks only.
- Planning output is a proposal: a generator behind `IPlanningGenerator` returns a draft, pure `PlanningDraftRules` repair it once and derive review states on every read, edits add immutable revisions, and only the confirmed `ActionConfirmation` of one revision creates entities. An `ActionConfirmation` has exactly one subject (a Reconcile session or a planning draft revision). See `step-08-planning-acceptance.md`. A generated draft must be approvable as handed over: the gate asks for a fault once more, and otherwise leaves out the faulty items and names them in `removedItems`. Judging repeats until nothing blocks; nothing is re-dated, re-typed or re-parented. The user never sees a structural error from the model (029 §8). A change to the planning prompt, contract, rules or model is kept only after `tools/planning-eval` meets the 029 §10 bar.
- A planned week is a `PlanningWindow` (029 §3, 014 §4.5): one per applied draft that planned a Goal or a standalone Project, retention R1. Its dates, offer and evidence rules live only in `PlanningContinuationRules`. It is offered from its second-to-last day until seven days after its end, through `GET /planning/continuations`, with counts of what happened. Nothing is generated until «برنامهٔ هفتهٔ بعد» starts an attempt with `continuationOfWindowId`, and the draft goes through the ordinary review and confirmation. Decisions use the 014 vocabulary on the previous week: approving records `CONTINUE_AS_IS`, or `ADJUST` after a user edit; «فعلاً نه» records `PAUSE_OR_STOP`; a new plan for the same scope records `REPLANNED` on its open weeks. Inside a Goal, the model places work under an existing Project by its `contextProjectRef` (P1…), stored as `ContextProjectId`. The gate drops a Task whose title repeats an open Task (`DROP_DUPLICATE_TASK`). Tests reach a week's end with the loopback-only `POST /api/v1/dev/planning-windows/rewind`.
  - **Dating an existing Task (014 note).** Any draft with a scope may give an existing open Task a day. The model names it by `existingTaskRef` (`T1…`), and it is stored as a TASK proposal with `ExistingTaskId`.
    - Title, owner and deadline come from the planner. A revision changes only its day and inclusion.
    - The preview hash covers the Task's version. Apply locks the Task and refuses with `CONFIRMATION_STALE` if it changed.
    - A Task that already had a date is moved with `TASK_CARRIED`; an undated one gets `TASK_UPDATED` (`plannedDate`).
    - `PLANNING_DRAFT_APPLIED` v3 counts these as `datedTaskCount`, and the result lists them as `datedTaskIds`, not `taskIds`.
  - The scope in the context carries its approved meaning and target date (`PlanningScope.Meaning`, `TargetDate`).
  - The gate rules for a next week are listed in `step-09-ai-planning-acceptance.md` 13g.
- A model is reached only through `IAiCompletionClient` (text in, text out, one HTTP call, no tool or function, no hidden retry). Prompt renderers and output gates are pure and take immutable DTOs; model text becomes a result only through the whole output gate, and a rejected output is never used in part. One logical operation is run by `AiOperationRunner` for every output family: at most two provider calls under one pinned configuration (the second after a transient failure or, for planning, after a rejected output, with the gate's correction added to the instructions), each preceded by the kill-switch, spend-cap, circuit and budget checks of that family and recorded as an `AiInvocations` metadata row. Gates share `AiOutputText` for wrapper removal and strict parsing. See `step-09-ai-planning-acceptance.md`.
- Reconcile AI is an optional layer behind `IReconcileExplainer`. Its context is built by pure code from one deterministic evaluation and holds codes, counts and flags only (no title, text, date or canonical id); it exists only when a rule matched. A recommendation may only name a matched rule and an action already allowed for every unit it points at, carries no number or date, and adds no authority: using it prefills the ordinary `ActionConfirmation` preview. Its disposition (`ACCEPTED`, `ACCEPTED_EDITED`, `REJECTED`) is stored apart from the command result. See `step-10-ai-reconcile-acceptance.md`.
- Operational evidence is read-only and aggregate-only, for accounts in `Operations:OperatorPhones` (`404` otherwise). A pilot metric is a versioned SQL definition in `PilotMetricCatalog` that returns numerator and denominator; acceptance is never counted as application. Product insights (027 §5) live in `ProductInsightCatalog`, versioned apart and run by the same `MetricQuery`; every rate there is shown «x از y» with its account-level figure first. Every entity has a class in `RetentionCatalog`; maintenance purges R4/R3/R2 and never R1 or canonical work; erasure tombstones the user id on R1 rows. See `step-11-operations-acceptance.md` and `operations/runbooks.md`.
- There is no AI consent step (Discussion 027): AI planning needs no agreement, and the manual path sends nothing to a model. Disclosure lives only on the privacy page, whose facts (whether planning text reaches a model, retention, erasure limit, contact) come from the running configuration through `GET /api/v1/pilot/notice`; changing its wording means changing `PrivacyNotice.Version`. The AI model or provider is never named in a user-facing response or screen, only on operator surfaces and in configuration. See `operations/runbooks.md`, runbook 9.
- The pilot runs as one backend instance on one server under Docker Compose (ADR-007): circuit, spend latch, concurrency, queues and the daily alert digest are per-process state. See `operations/deployment.md`.
- PostgreSQL/Npgsql is canonical; domain/application/API contracts remain provider-neutral.
- xUnit + real PostgreSQL (Testcontainers or configured local instance) + WebApplicationFactory; Vitest/Testing Library/Playwright.
- Local backend secrets use .NET User Secrets; real-PostgreSQL tests use user/process-scoped `TIDYSENSE_TEST_POSTGRES`. Use root `dev.ps1` commands; Vite proxies `/api` to backend HTTPS without broad local CORS.
- `development-steps.md` is the canonical execution roadmap. Start/Continue/Review commands stay inside one requested step, verify dependencies, update evidence only after checks pass, and never advance automatically.
- Load context progressively through `/AGENTS.md` → context routing → requested step → focused authorities → relevant code; do not rescan all DevMap/Mind Map/code by default.
- Prefer existing patterns/shared code, then small explicit feature code; extract only after real repetition.
- No dedicated crisis UX/gate. General provider safeguards, hostile-input isolation, minimized context, no diagnosis/AI mutation and manual fallback remain.
